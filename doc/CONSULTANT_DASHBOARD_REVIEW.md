# Taipei Friendly Food Map：顧問式產品與資料儀表板評估

> 評估日期：2026-08-18  
> 評估範圍：React/PWA 前端、資料轉換流程、已匯入的 Taipei Open Data、食品與農產品資訊儀表板。  
> 本文件提供產品與營運建議；不是食品安全、醫療、法規或採購建議。

## 給客戶的結論

這個產品的方向正確，而且已具備一個公共資訊服務應有的核心界線：**店家／設施查找**與**城市層級統計透明度**分開呈現。這一點很重要，因為它避免把「曾被抽驗的不合格統計」誤導成「某家店或某類商品一定有風險」。

目前最有價值的能力是讓市民在同一個入口完成兩種不同的任務：

1. 找到鄰近友善店家、飲水點與相關設施。
2. 了解政府對食品、農產品與商圈資訊的公開資料與年度趨勢。

下一階段不應急著再加更多圖層；應優先把資料新鮮度、比較脈絡、行動導向與效能做成可信賴的服務基礎。

## 農產品抽檢儀表板：可直接使用的洞察

目前匯入資料為「臺北市政府標章農產品抽檢清冊」，涵蓋民國 108–114 年（2019–2025）、28 筆彙總列。所有數字均為此份資料集的彙總，不可延伸為單一店家、品牌或整個市場的風險判定。

| 指標 | 觀察 | 實務解讀 |
|---|---:|---|
| 累計抽驗 | 8,439 件／場 | 可作為政府標章農產品的監測量級參考，而非市場總量。 |
| 已列合格 | 8,344 件／場 | 以合格／抽驗計算的累計加權合格率約 98.87%。 |
| 已列不合格 | 70 件／場 | 適合用於了解監測與改善的需求，不適合做恐慌式產品排序。 |
| 最新年度 | 2025：1,135 件／場、99.56% 加權合格率 | 最新年度抽驗量與前一年相近，合格率略低於 2024 的 99.82%。比較時應說「下降約 0.26 個百分點」，不是「下降 0.26%。」 |
| 類別結構 | 標示：5,520 件／場；品質：2,919 件／場 | 標示是較大的監測工作量；品質的加權合格率較低（98.70% vs. 98.97%），但兩者差距須搭配抽驗範圍與法規定義解讀。 |

### 必須保留的資料註記

全期「抽驗件數／場」8,439 與「合格＋不合格」8,414 之間有 **25 件／場差額**。目前轉換器正確地不把缺少的數字假設為零，且未修改官方原始資料。對使用者而言，建議在 KPI 或方法說明中明確寫出：

> 「合格率依已提供的合格件數／場與抽驗件數／場加權計算；部分列的合格與不合格合計可能小於抽驗總數，因此未分類差額不會自動歸入任一結果。」

這個註記能避免外部利害關係人把儀表板數字誤解為完整的結果分布。

## 最值得優先處理的五件事

## 上線前的實作與營運檢視

本次檢視涵蓋 25 個應用程式與資料處理檔案，並已確認 production build 與 8 個既有自動測試均通過。未發現硬編碼機密、危險的 HTML 插入或明顯的用戶輸入執行路徑。不過，下列事項會直接影響客戶信任與正式上線品質。

| 優先級 | 發現 | 客戶影響 | 建議處置 |
|---|---|---|---|
| 上線阻擋 | `data:fetch` 與 `convert:data` 的全量流程沒有包含傳統市場與超市資料；雖有各自腳本，但例行全量更新會漏掉它們。 | 公開資料網站可能在不報錯的情況下發布舊資料或缺少資料。 | 將兩類資料加入全量流程，並把該流程明確定義為唯一的例行更新方式。 |
| 上線阻擋 | 傳統市場已在導覽列出現，也有摘要載入設定，但沒有對應頁面元件；已提交的 generated data 亦不存在。 | 使用者會進入空白／無內容頁面，展示或正式服務都會被視為未完成。 | 在完整交付（資料、元件、測試）前先隱藏該頁籤；或優先完成端到端模組。 |
| 高優先 | 初始應用程式會預先載入所有儀表板；目前 production JavaScript 約 531 kB（minified）並有建置警告。 | 手機、行動網路與首次使用的體驗會受到不必要拖累。 | 依頁籤使用動態載入，先交付地圖／核心查找，再載入次要儀表板。 |
| 高優先 | Service Worker 預先快取沒有涵蓋農產品抽檢與超市的資料檔。 | 新安裝且離線的 PWA 在不同頁面會有不一致的可用性。 | 快取清單與版本要隨可見模組同步更新，並在實機離線情境驗收。 |
| 一般 | README 宣稱有 CI workflow，但目前找不到該檔案。 | 維護者與採購／合作方可能高估發布防護程度。 | 補上 CI（安裝、build、test）或移除該敘述。 |

這些不是視覺微調，而是公共資訊服務的「可靠交付」問題。建議先解決前兩項，再評估新增任何資料集。

### 1. 建立資料更新的服務承諾

**建議：** 在每個資料模組顯示「來源更新日、本站更新日、下次預計檢查日」，並以每月或每季排程檢查來源變更。

**原因：** 使用者最常問的不是「有沒有資料」，而是「這是不是最新」。目前資料轉換已可重複執行，但尚未形成固定更新節奏或來源變更告警。

**成功指標：** 95% 以上資料集在其承諾更新週期內完成檢查；更新失敗可被記錄與通知。

### 2. 讓資料導向下一步，而非只提供圖表

**建議：** 為每一個模組增加一個「如何使用此資訊」區塊。例如：

- 找店家：以距離、無障礙、素食、友善服務等條件篩選，再自行確認營業狀態。
- 看抽檢：看年度、類別與樣本數的變化，必要時連回主管機關公告查閱原因與後續處置。
- 看溯源：用來查找產品與成分來源資訊，不把它解讀成產品推薦或安全保證。

**原因：** 圖表本身不一定改變行為；清楚的下一步才能讓公開資料真正被使用。

**成功指標：** 觀察「篩選後點擊資料來源／地圖／店家」的比率，以及使用者是否完成預期任務。

### 3. 把新鮮度與資料限制做成一致的信任介面

**建議：** 全站採用一致的資料卡：來源、涵蓋期間、更新時間、資料層級（店家／產品／城市統計）、不可推論事項。

**原因：** 目前各模組已有不少負責任的說明，但使用者需要一眼辨認資料是「目前狀態」、「歷史紀錄」或「年度統計」。

**成功指標：** 用戶測試中，至少 80% 受訪者能正確回答某一資料集是否能代表即時營業、食安評等或特定店家。

### 4. 優先改善手機首次載入與離線體驗

**建議：** 將較大的資料檔延後到使用者開啟對應頁籤或進行搜尋時才載入；為每個新增模組更新 Service Worker 的快取清單與版本；量測 4G 手機上的首次可互動時間。

**原因：** 專案目前會服務數 MB 等級的店家與餐飲資料，且 Service Worker 的預先快取清單尚未列入農產品抽檢 JSON。線上時可由資料請求快取補足，首次離線安裝後則不保證農產品頁面可用。

**成功指標：** 中階手機 4G 的主要地圖可在 3 秒內可互動；離線安裝後，承諾可離線的模組均能載入。

### 5. 為資料處理加上自動化品質保證

**建議：** 為每一類資料轉換器增加最少三種測試：欄位／編碼解析、關鍵衍生計算、異常列旗標。農產品模組優先測試 Big5/CP950 解碼、百分比清理，以及加權合格率。

**原因：** 公開資料最常見的實際故障是欄位改名、編碼改變、空值或格式變動。既有轉換腳本已做了不少防護，測試能把這些防護變成可持續驗證的契約。

**成功指標：** 來源格式變動時，轉換在發布前明確失敗並輸出可理解原因，而不是產生不完整資料。

## 90 天可行路線圖

| 時間 | 重點 | 交付物 |
|---|---|---|
| 0–30 天 | 信任與資料治理 | 統一資料卡、農產品差額註記、資料更新責任表、轉換器測試。 |
| 31–60 天 | 任務導向體驗 | 各模組的「如何使用」、分享／下載篩選結果、可理解的空資料與更新失敗狀態。 |
| 61–90 天 | 效能與成效 | 延後載入大型資料、PWA 離線驗收、隱私友善的事件量測、以任務完成率優化導覽。 |

## 建議追蹤的成效指標

- **任務完成率：** 使用者能否在 2 分鐘內找到符合條件的場所，或回答一個年度／類別抽檢問題。
- **資料信任度：** 使用者是否理解資料時間、粒度與不可推論事項。
- **資料新鮮度：** 每個資料集最近檢查日與來源更新日的差距。
- **效能：** 手機首次可互動時間、主要資料載入失敗率、離線可用率。
- **回訪價值：** 從儀表板前往來源公告、篩選結果下載、店家地圖查詢的比例。

## 顧問的優先判斷

這不是一個只需要「更多資料」的產品，而是一個需要**更明確可信任契約**的公共資訊服務。若先把更新節奏、資料限制、行動導向與手機效能做好，未來新增市場、餐廳、食材或政策資料時，才能維持一致、可被市民理解且可長期維護的服務品質。
